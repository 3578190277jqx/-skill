# 评审问答与证据缺口

默认提出 10 个最可能追问的问题；用户指定数量优先。优先追问材料里的实际矛盾、缺证据的结论和学生需要解释的技术取舍，不给与项目无关的通用题库。

建议覆盖：选题价值、真实用户/需求来源、架构取舍、数据库约束、关键流程及失败分支、核心实现、测试条件与结论、特色与对比、本人贡献、局限与改进。没有相关模块时替换题目，不凭空加入 Redis、AI、权限或分布式架构。

每题输出以下内容：

| 内容 | 要求 |
|---|---|
| 问题与触发点 | 指出哪一页/章/主张容易引发追问 |
| 可直接说的回答 | 口语化 30–60 秒，依据实际材料 |
| 证据 | 文件、页码、图号、代码或测试记录位置 |
| 下一层追问 | 追问实现细节或方案取舍 |
| 当前缺口与补法 | 缺证据就写“目前答不上来”，给具体补证方法 |

将“能可靠回答”“有合理设计但待验证”“目前没有材料支持”分开。不得把推测的功能写成已实现，不替学生编造实验或个人经历。

完整任务结束时给出少量优先补齐项，以影响答辩可信度排序。例如“补一次可复现测试及条件”比“再加装饰图标”优先。问答与 PPT、论文、ER 的名称和指标必须一致。
